# Backend API contract

This is what the frontend expects from the backend. The frontend client lives in `src/api/client.js`; every request goes through it.

- Base path: `/api`. In development, Vite proxies `/api` to `http://localhost:8080` (`vite.config.js`), so there's no CORS setup needed locally. In production, either serve both from the same origin or set `VITE_API_URL` at frontend build time (then you need CORS).
- All bodies are JSON unless noted.
- Auth: every endpoint except those marked **public** expects `Authorization: Bearer <token>`.
- Errors: any non-2xx status. If the body is JSON with a `message` (or `error`) field, the frontend shows that text. A **401** on any endpoint (except login) logs the user out and redirects to `/Acceso`.

## 1. Auth

### `POST /api/auth/login`: **public**
```json
// request
{ "usuario": "pepe", "contrasena": "secreto" }
// 200 response
{
  "token": "<JWT or any opaque token>",
  "sesion": {
    "integranteId": "abc123",
    "nombre": "Pepe Pérez",
    "cargo": "tesorero",        // null | presidente | vicepresidente | tesorero | secretario | vocal | ...
    "avatarUrl": "/api/files/x.jpg",  // or null
    "esAdmin": false,
    "soloLectura": false         // optional; the UI shows a read-only banner in Admin
  }
}
```
- Look up the `SesionUsuario` whose `usuario` matches (case-insensitive). Reject it if `disabled`, and check the password against the stored **hash**.
- `nombre` and `cargo` come from the `Integrante` with `id = sesionUsuario.integrante_id`.
- The special username `__admin__` logs in as admin (`integranteId: "__admin__"`, `nombre: "Admin"`, `esAdmin: true`). Its password should come from backend config/env, not code.
- Wrong credentials: 401 with `{ "message": "Usuario o contraseña incorrectos" }` (shown as-is).

### `GET /api/auth/me`
Returns the same `sesion` object for the current token. It's called after the avatar changes.

### `GET /api/auth/usuarios`: **public**
This feeds the quick user picker on the login page. Return only **active** accounts (a `SesionUsuario` exists and isn't `disabled`) whose `Integrante.categoria != "patitas"`:
```json
[ { "id": "<integranteId>", "nombre": "Pepe Pérez", "usuarioLogin": "pepe" } ]
```
`usuarioLogin` is `SesionUsuario.usuario`, falling back to `Integrante.nombre`.

Logout is client-side only (the token is discarded).

## 2. Entities (generic CRUD)

Every entity uses the same URL pattern: `/api/entities/{Entity}`, where `{Entity}` is the PascalCase name used in the frontend (`Integrante`, `ChatMensaje`, …; full list below).

### Record shape
A record is a flat JSON object with the entity's own fields plus these system fields, which the backend sets:

| field | notes |
|---|---|
| `id` | string; generated by the backend |
| `created_date` | ISO-8601 timestamp; the frontend sorts on it a lot |
| `updated_date` | ISO-8601 timestamp |
| `created_by_id` | id of the user who created it (`sesion.integranteId`) |

Field names are snake_case (`integrante_id`, `fecha_entrega`, …). Clients may send arbitrary fields. The real field lists per entity aren't in this repo, so look at what each frontend component reads and writes.

### Endpoints

| Method & path | Frontend call | Description |
|---|---|---|
| `GET /api/entities/{E}` | `list(sort, limit, skip)` / `filter(query, sort, limit, skip)` | Returns a JSON **array**. |
| `GET /api/entities/{E}/{id}` | `get(id)` | Returns one record, or 404. |
| `POST /api/entities/{E}` | `create(data)` | Returns the created record (with `id` etc.). |
| `POST /api/entities/{E}/bulk` | `bulkCreate(items)` | Body is an array. Returns the created records **in the same order**. |
| `PATCH /api/entities/{E}/{id}` | `update(id, data)` | **Partial** update: merge the given fields and keep the rest. Returns the updated record. |
| `DELETE /api/entities/{E}/{id}` | `delete(id)` | 204 (or 200). |
| `POST /api/entities/{E}/delete-many` | `deleteMany(ids)` | Body `{ "ids": ["..."] }`. 204. Used by backup restore. |
| `GET /api/entities/{E}/schema` | `schema()` | Optional. Returns a JSON Schema-like description of the fields. It's only used by the admin "Código" panel, which tolerates failures. |

### Query parameters for `GET /api/entities/{E}`
- `sort`: a field name, optionally prefixed with `-` for descending. Examples: `-created_date` (by far the most common), `-fecha`, `-anio`, `nombre`, `clave`. Sort numbers numerically and strings alphabetically.
- `limit`, `skip`: optional integers. With no `limit`, return everything. Backup export pages through with `limit=500&skip=…` and stops when it gets fewer than `limit`.
- **Every other parameter is an equality filter** on that field, ANDed together. Values arrive as strings, so compare them against the field's type: `completada=false` should match the boolean `false`, and `anio=2026` the number 2026. Filtering on `id` must work too. Examples in the code: `?clave=app_nombre`, `?integrante_id=abc`, `?grupo_id=x&sort=created_date`, `?integrante_id=abc&tipo=pago`.
  `sort`, `limit` and `skip` are reserved names, so no entity field can be filtered with them.

### Special rules for `SesionUsuario` (login accounts)
Fields: `integrante_id`, `usuario`, `contrasena`, `disabled`, `avatar_url`.
- `contrasena` is **write-only**. On create and update, hash it (e.g. BCrypt) and **never** return it in any response.
- Who may write: admins (`esAdmin`, `presidente`, `vicepresidente`) can create, update and delete any account. A regular user may only update **their own** account (`integrante_id` = their `integranteId`), and only the `contrasena` and `avatar_url` fields (the profile page changes the password and avatar this way).
- Anything else returns **403** with `{ "message": ... }` (e.g. `"Solo puedes modificar tu propia cuenta"`, `"Solo puedes cambiar tu contraseña y tu avatar"`). The permission check runs before validation, so a user without permission gets 403 rather than a 400 like `"Ese usuario ya existe"`. Reading accounts (`list`/`filter`/`get`) is open to any authenticated user.

### Special rules for beer (`ConsumoCerveza`, `CervezaPago`)
There is no per-person beer counter. A person's beers are the sum of `cantidad` of their `ConsumoCerveza` rows with `archivado=false`, and what they have paid is the sum of `importe` of their `CervezaPago` rows with `archivado=false` (`src/lib/cerveza.js` does the maths).
- Both are linked to a member by `integrante_id` (foreign key to `Integrante`). `integrante_id: null` means the guests ("Invitados").
- `ConsumoCerveza`: `cantidad` (integer > 0, required), `integrante_id`, `tipo` (may be null), `archivado`, `anio_archivo`. Any authenticated user may create, update and delete.
- `CervezaPago`: `importe` (required, not 0, **may be negative**: discounts and manual corrections are stored as negative payments), `integrante_id`, `fecha` (ISO instant), `notas`, `archivado`, `anio_archivo`. Reading is open to any authenticated user; writing (create, update, delete) only to admins (`esAdmin`, `presidente`, `vicepresidente`), otherwise **403**.
- Closing the year does not delete anything: the frontend PATCHes every open consumption and payment with `{ archivado: true, anio_archivo }`.
- An unknown `integrante_id` returns **409**, and so does deleting an `Integrante` that still has beer consumptions or payments.

`AppConfig` is a key/value store (`clave`, `valor`, where `valor` is often a JSON string). It holds app settings: colours, name, menu labels, disabled pages and so on.

**Implementation tip:** you don't need 58 hand-written controllers to get the app running. A common approach is one generic controller for `/api/entities/{entity}`, backed by a table that stores each record as JSON (PostgreSQL `jsonb`). Then give the important entities (`SesionUsuario`, `Integrante`, the finance ones) their own JPA entity and controller. Spring picks the more specific mapping (`/api/entities/SesionUsuario`) over `/api/entities/{entity}`.

## 3. Real-time updates

### `GET /api/events?token=<token>`
This is a Server-Sent Events stream (`text/event-stream`). Browsers' `EventSource` can't send headers, so the token comes as a query parameter. The frontend opens **one** stream and keeps it open while something is subscribed.

Send each change to an entity as a default (unnamed) SSE message whose `data` is:
```json
{ "entity": "ChatMensaje", "type": "create", "id": "<record id>", "data": { ...full record... } }
```
`type` is `create`, `update` or `delete` (for `delete`, `data` may be just `{ "id": ... }`).

The frontend currently listens to: `ChatMensaje` (live chat), `Tarea`, `Votacion`, `ActaReunion` and `Actividad` (browser notifications on `create`). Broadcasting every entity is fine.

## 4. Files

### `POST /api/files`
Multipart form with one field, `file`. Returns:
```json
{ "file_url": "/api/files/3f2a…-foto.jpg" }
```
The URL is stored in records and used directly in `<img src>`, `<a href>` and `<video>`, so **`GET` on that URL must be public** (browsers don't send the bearer token for images). Use unguessable names (e.g. a UUID). Uploads include photos, PDFs and other documents.

## 5. AI (optional)

### `POST /api/ai/llm`
```json
// request
{ "prompt": "…", "response_json_schema": { "type": "object", "properties": { "emoji": { "type": "string" } } } }
// response
{ "result": "plain text answer" }          // when no schema was sent
{ "result": { "emoji": "📦" } }             // when response_json_schema was sent
```
This powers the "Cholín" chat assistant (`Chat.jsx`), the admin AI helper (`IACreador.jsx`) and emoji suggestions for warehouse categories.

### `POST /api/ai/image`
```json
// request
{ "prompt": "Simple flat icon for…" }
// response
{ "url": "/api/files/icon-….png" }
```
This generates warehouse category icons. Until it's implemented, those buttons simply fail.
